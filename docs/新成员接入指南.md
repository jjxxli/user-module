# 新成员接入指南

> 给第一次参与「统考 408 刷题软件 · 用户模块」的同学：跟着本文从零配置环境、跑通项目、走完一次「开分支 → 提交 → PR → 评审 → 合并」的完整流程。
> 预计用时：**30～60 分钟**（不含下载依赖）。遇到问题先看第 7 节常见问题，再找 Owner。
>
> 配套文档：[README.md](../README.md)（项目介绍与快速开始）、[CONTRIBUTING.md](../CONTRIBUTING.md)（编码与 PR 规范）、[docs/协作规范.md](协作规范.md)（完整协作规则）。

---

## 0. 先决条件（逐项自检）

| 依赖 | 要求 | 自检命令 | 不满足怎么办 |
| --- | --- | --- | --- |
| JDK | 17（推荐 Temurin） | `java -version` | 装 JDK 17 并配 `JAVA_HOME` |
| Git | 建议 2.40+ | `git --version` | 安装 Git；Windows 选 Git for Windows |
| Git Bash | Windows 需要（钩子是 `sh` 脚本） | 开始菜单搜索 Git Bash | 重装 Git for Windows 时勾选 |
| MySQL | 8.x（本地开发） | `mysql --version` | 安装 MySQL 8；只跑测试可不装 |
| GitHub 权限 | 已被 Owner 邀请为 collaborator | 能打开 <https://github.com/jjxxli/user-module> 并看到 Settings/分支 | 群里找 Owner（`jjxxli`）邀请 |
| DSH / AI 助手 | 可选，推荐（第 6 节提供提示词） | 能新建会话 | 用任何终端 + 本文手动操作 |

> 不需要单独安装 Maven：项目自带 Maven Wrapper（`mvnw` / `mvnw.cmd`）。

**总流程一览**：

1. 克隆仓库、配置 Git 身份、安装钩子；
2. 配置本地 MySQL 与 `application-local.yml`；
3. 跑测试、启动应用、用 `api-test.http` 验证；
4. 在 Issue 中领任务 → 切分支 → 小步提交 → push；
5. 在 GitHub 开 PR（填模板）→ 等 CI + 评审 → Owner 合并；
6. 同步 `main`、删本地分支，开始下一个任务。

## 1. 克隆仓库、配置身份、安装钩子

### 1.1 克隆

```bash
git clone https://github.com/jjxxli/user-module.git
cd user-module
```

建议放英文无空格路径（例如 `E:\IDEA-project\user-module`），避免 Maven / 钩子路径问题。

### 1.2 配置 Git 身份（必须用自己的名字和邮箱）

```bash
# 只对本仓库生效（推荐）
git config user.name "你的名字"
git config user.email "你的邮箱@example.com"

# 确认
git config --get user.name
git config --get user.email
```

> 不要使用别人的身份提交；邮箱建议与 GitHub 账号一致。若想全局配置，用 `git config --global`。

### 1.3 安装 Git 钩子（每台机器一次）

```powershell
# Windows PowerShell（任选其一）
.\scripts\install-hooks.ps1
# 若提示「禁止运行脚本」：powershell -ExecutionPolicy Bypass -File scripts/install-hooks.ps1
git config core.hooksPath .githooks
```

```bash
# Git Bash / macOS / Linux（任选其一）
bash scripts/install-hooks.sh
git config core.hooksPath .githooks
```

> PowerShell 不支持 `mysql ... < 文件` 的输入重定向：可以先用 `mysql -u root -p` 登录再执行 `source E:/IDEA-project/user-module/src/main/sql/user_module_mysql.sql`，或执行 `Get-Content src/main/sql/user_module_mysql.sql | mysql -u root -p`。

验证：

```bash
git config --get core.hooksPath    # 应输出 .githooks
```

钩子会在本地拦截：

- 在 `main` 上直接提交；
- 大于 5 MB 的文件；
- 敏感文件：`*.env`、`.env*`、`*.pem`、`*.key`、`id_rsa*`、`application-local.yml`；
- 行尾空白 / 冲突标记（`git diff --cached --check`）；
- 不符合 Conventional Commits 的提交信息；
- 直接 `git push` 到 `main`。

> 钩子只是第一道防线，**不要用 `--no-verify` 绕过**。GitHub 上 `main` 还有分支保护。

### 1.4 阅读项目文档（10 分钟）

至少看一遍：

- `README.md`：技术栈、目录结构、快速开始；
- `CONTRIBUTING.md`：编码规范与 PR 检查清单；
- `docs/协作规范.md`：分支模型、提交规范、评审流程；
- `docs/功能模块结构.md`：模块划分与当前进度。

## 2. 配置本地数据库

### 2.1 建库建表（含演示账号）

```bash
mysql -u root -p < src/main/sql/user_module_mysql.sql
```

脚本会创建 `userdb` 数据库、`t_user` 表，并预置演示账号 `demo / 123456`。

### 2.2 复制本机配置模板

```powershell
# Windows PowerShell
Copy-Item src/main/resources/application-local.yml.example src/main/resources/application-local.yml
```

```bash
# Git Bash / macOS / Linux
cp src/main/resources/application-local.yml.example src/main/resources/application-local.yml
```

### 2.3 填入自己的 MySQL 账号密码

编辑 `src/main/resources/application-local.yml`，把 `username` / `password` 改成**你本机**的 MySQL 账号密码。

- `application.yml` 只放占位符，**不要**在里面写真实密码；
- `application-local.yml` 已被 `.gitignore` 忽略、也被钩子拦截，**永远不会提交**；
- 如果你不想改文件，也可以用环境变量 `MYSQL_URL` / `MYSQL_USERNAME` / `MYSQL_PASSWORD` 注入（见 `application.yml` 注释）。

## 3. 跑测试、启动、验证

### 3.1 先跑测试（不依赖 MySQL，走 H2）

```powershell
.\mvnw.cmd -B -ntp verify
```

```bash
./mvnw -B -ntp verify
```

看到 `BUILD SUCCESS` 说明环境 OK。这个命令与 CI 完全一致；Linux / macOS 若提示 `mvnw: Permission denied`，执行 `chmod +x mvnw`。

### 3.2 启动应用

```powershell
.\mvnw.cmd spring-boot:run
```

```bash
./mvnw spring-boot:run
```

启动成功后监听 **8080** 端口。

### 3.3 验证接口

用 IDEA 打开根目录 `api-test.http`（HTTP Client）逐个运行，或：

```bash
curl -X POST http://localhost:8080/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"test01","password":"123456","confirmPassword":"123456","nickname":"测试一"}'

curl -X POST http://localhost:8080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"demo","password":"123456"}'
```

预期：注册成功返回 `{"code":200,"message":"注册成功，请登录",...}`；登录成功返回 `{"code":200,"message":"登录成功",...}`。

> Windows PowerShell 里 `curl` 是 `Invoke-WebRequest` 别名，请用 `curl.exe`，或直接用 `api-test.http`。

## 4. 领任务、开分支、提交

### 4.1 找任务

打开 GitHub Issues，找适合自己的任务（标签 `good first issue` 适合第一次做）；没有合适的就在群里问 Owner。新建 Issue 时使用仓库模板（Bug 报告 / 功能需求 / 开发任务；空白 Issue 已禁用）。领取方式：在 Issue 下评论「我来做」，让自己成为 Assignee。

### 4.2 从最新 main 切分支

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/login-jwt
```

分支命名：`feature|fix|docs|refactor|chore|hotfix/` + 小写英文 kebab-case，例如 `feature/login-jwt`、`fix/register-dup`、`docs/update-readme`。

### 4.3 开发并小步提交

```bash
# 改代码 / 文档……
git status
git diff --cached

git add <改动的文件>
git commit -m "feat(auth): 实现登录接口并写入 Session" -m "Closes #12"
```

提交信息格式（钩子会校验）：

```text
<type>(<scope>): <中文 subject，≤50 字，不加句号>
```

- type ∈ `feat` `fix` `docs` `style` `refactor` `perf` `test` `build` `ci` `chore` `revert`
- scope 建议 `auth` `user` `common` `config` `docs` `ci` `deps`
- 关联 Issue 在 footer 写 `Closes #12`

### 4.4 推送到自己的分支

```bash
git push -u origin feature/login-jwt
```

**禁止** `git push origin main`；**禁止** `git push --force`（同步 main 时用 `--force-with-lease`，见 CONTRIBUTING.md）。

## 5. 开 PR、等评审、合并

### 5.1 创建 PR

在 GitHub 仓库页面会看到「Compare & pull request」提示；或访问：

```text
https://github.com/jjxxli/user-module/compare/main...feature/login-jwt
```

PR 要求：

- 标题符合提交规范，例如 `feat(auth): 实现登录接口并写入 Session`；
- 按 `.github/PULL_REQUEST_TEMPLATE.md` 完整填写：**变更内容 / 关联 Issue / 变更类型 / 自测方式 / 影响范围与兼容性 / 提交前检查清单**；
- 关联 Issue：正文写 `Closes #12`；
- 草稿阶段可先 Draft，准备好后点「Ready for review」。

PR 模板示例（可直接参考）：

```text
## 1. 变更内容
- 新增 POST /api/auth/login，校验用户名和 BCrypt 密码，成功后写入 Session
- 补充登录失败（用户不存在 404 / 密码错误 400）的异常返回
- 更新 api-test.http 登录用例

## 2. 关联 Issue
Closes #12

## 3. 变更类型
- [x] feat 新功能

## 4. 自测方式
- .\mvnw.cmd -B -ntp verify 通过
- 启动后用 api-test.http 第 5～7 条验证：不存在用户返回 404、密码错误返回 400、正确返回 200

## 5. 影响范围与兼容性
- 影响模块：M1 用户与登录
- 接口：新增 /api/auth/login
- 数据库：无变更
- 配置：无变更

## 6. 提交前检查清单
- [x] 已在本地跑通 .\mvnw.cmd -B -ntp verify
- [x] 未提交 application-local.yml、密码、密钥、大文件
- [x] 分层、统一异常、参数校验符合规范
- [x] 已更新 api-test.http
```

### 5.2 等待 CI 与评审

- CI：`.github/workflows/ci.yml` 的 job **`build`** 必须变绿；
- 评审：至少 **1 名非作者成员 Approve**，所有评论已解决；
- 响应时效：Reviewer 24 小时内给首轮意见；作者 24 小时内处理评论。

Reviewer 反馈后：本地修改 → `git add` → `git commit` → `git push`（PR 自动更新）→ 在 PR 里回复「已处理」并重新请求评审。

> 仓库用 `.github/CODEOWNERS` 自动指派审查人（当前默认 Owner 兜底，组员确定后按模块补充）；如果没收到评审请求，在群里 @ 对应模块负责人。若分支保护启用了「Require review from Code Owners」，CODEOWNERS 中的负责人必须 Approve。

### 5.3 合并与收尾

- Owner 用 **Squash and merge** 合并，远端分支自动删除；
- 本地同步并清理：

```bash
git switch main
git pull --ff-only origin main
git branch -d feature/login-jwt
git fetch --prune
```

- 检查 Issue 是否已自动关闭；没有则手动关闭并说明。

## 6. 使用 DSH / AI 助手（可直接复制的提示词）

### 6.1 怎么用

1. 在**本机项目根目录**（例如 `E:\IDEA-project\user-module`）打开 DSH / AI 助手的新会话，这样助手直接操作仓库；
2. 从下面选择对应场景的提示词，**整段复制**粘贴；
3. 把 `<尖括号里的占位符>` 换成你的实际信息（Issue 编号、分支名、姓名邮箱等）；
4. 助手执行命令前会先说明计划；**涉及 git push / 创建 PR 时，确认它推的是你的功能分支**；
5. 助手产出的代码你要自己看懂再合并——答辩可能被追问，不要交给自己没理解的代码。

> 提示：如果助手没有执行命令的权限，让它输出命令清单，你手动粘贴到 Git Bash / PowerShell 执行。

### 6.3 提示词 ②：领一个任务并开 PR

```text
你是我的编程助手，帮我按团队规范完成一个 GitHub Issue 并创建 Pull Request。

【项目事实】
- 本机仓库路径：<E:\IDEA-project\user-module>
- 远端仓库：https://github.com/jjxxli/user-module （默认分支 main，受保护，禁止直接 push，只能通过 PR 合并）
- 技术栈：Spring Boot 3.3.5 + MyBatis + MySQL 8 + Java 17，Maven Wrapper
- 任务：Issue #<编号> <标题>；<把 Issue 正文或我的补充要求贴在这里>

【规矩（必须遵守）】
- 从最新 main 切短期分支，命名：<前缀>/<kebab-case>，前缀只允许 feature|fix|docs|refactor|chore|hotfix，例 feature/login-jwt；禁止在 main 上提交。
- 提交信息用 Conventional Commits：type(scope): 中文 subject（≤50 字、不加句号），type ∈ feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert，scope 建议 auth|user|common|config|docs|ci|deps。
- 小步提交：一个提交只做一件事，禁止一次提交几十个文件。
- 禁止提交任何密码、密钥、Token、.env、*.pem、*.key、application-local.yml、大文件（>5MB）。
- 禁止 git push --force、禁止 push main、禁止使用 --no-verify 绕过钩子。

【执行步骤】
1. git switch main && git pull --ff-only origin main && git switch -c <分支名>
2. 先读懂相关代码再改：Controller 只收参和返回、业务写在 Service、SQL 在 mapper XML、DTO 带 jakarta 校验注解、返回统一 Result、异常用 BizException。
3. 分步实现，每完成一个可验证的小步就提交一次，提交前用 git status / git diff --cached 自检暂存内容。
4. 运行全部测试：Windows PowerShell 用 .\mvnw.cmd -B -ntp verify，Git Bash 用 ./mvnw -B -ntp verify，必须 BUILD SUCCESS 才能继续。
5. 如果新增或修改了接口，同步更新根目录 api-test.http；如涉及配置/流程变化，同步更新相关文档。
6. 推送前先自检：git status、git diff、本地 verify 全部通过。
7. 推送我的分支：git push -u origin <分支名>（只推这个分支，不要推 main，不要 force）。
8. 准备 PR 标题与完整描述（写入 .git/pr-body.md），按仓库 PR 模板填写六部分：变更内容、关联 Issue（Closes #<编号>）、变更类型、自测方式、影响范围与兼容性、提交前检查清单。先停下来把标题和描述给我确认。
9. 我确认后再创建 PR（优先用 gh CLI）：
   gh pr create --base main --head <分支名> --title "<type(scope): 标题>" --body-file .git/pr-body.md
   如果本机没有 gh，就给我 compare 网页链接，让我手动创建。

【完成后输出】
- 分支名、提交列表（含提交信息）、测试命令与结果、PR 链接
- 需要我人工确认或注意的风险点
- 如果有任何一步失败，说明失败原因、已尝试的修复，不要静默跳过。
```

### 6.4 提示词 ③：做 Reviewer（审查别人的 PR）

```text
你是我的代码评审助手，帮我按团队规范审查一个 Pull Request，给出具体可执行的评审意见。

【项目事实】
- 本机仓库路径：<E:\IDEA-project\user-module>
- 远端仓库：https://github.com/jjxxli/user-module （main 受保护，只允许 Squash and merge）
- 待审 PR：#<编号>（链接：<PR 链接或留空>），作者：<作者>，目标分支：main

【获取改动】
- 有 gh CLI：gh pr view <编号> --json title,body,files,baseRefName,headRefName,author,commits
  然后 gh pr diff <编号>
- 没有 gh：git fetch origin pull/<编号>/head:review/pr-<编号>，再 git diff origin/main...pr-<编号>

【审查清单】
1. 分支命名是否符合 feature|fix|docs|refactor|chore|hotfix 前缀 + 小写 kebab-case；PR 是否从 main 切出。
2. 提交信息是否符合 Conventional Commits（type/scope/中文 subject ≤50 字），是否有 Closes #N；Commit 是否小步、聚焦。
3. 是否夹带敏感信息：密码、密钥、Token、.env、*.pem、*.key、application-local.yml、大文件、target/、.idea/。
4. 分层是否清晰：Controller 只收参/校验/返回，业务在 Service，SQL 在 mapper XML 且用 #{} 预编译参数（禁止 ${} 拼接用户输入），DTO 与 Entity 分离。
5. 参数校验是否使用 jakarta.validation + @Valid；异常是否走 BizException / GlobalExceptionHandler；接口是否统一返回 Result。
6. 是否把密码明文或密文返回前端、是否把敏感信息写进日志、是否泄露堆栈。
7. 新增业务是否有对应测试；测试是否 @ActiveProfiles("test") 且不依赖本地 MySQL。
8. 接口变更是否同步更新 api-test.http；文档 / 配置变更是否同步。
9. 是否存在明显 bug、空指针、边界条件（空值、重复、并发）、事务缺失。
10. 是否已满足合并条件：CI job build 绿灯、无未解决评论、至少 1 人 Approve。

【输出格式】
- 结论：通过 / 需修改
```

## 7. 第一次参与常见问题

### Q1：`git push` 返回 403 / 没有权限？

你还没有被加为 collaborator。把 GitHub 用户名发给 Owner（`jjxxli`），Owner 会运行 `scripts/add-collaborators.ps1` 邀请你（默认 push 权限）；到 GitHub 通知页接受邀请后再 push。**不要**自行 fork 后往主仓库提 PR 当成默认流程。

### Q2：`mvnw: Permission denied`？

Linux / macOS / Git Bash 下执行 `chmod +x mvnw`；Windows 用户也可以直接用 `.\mvnw.cmd`。

### Q3：启动报 `Access denied for user 'root'@'localhost'`？

`application-local.yml` 里的 `username` / `password` 不是本机 MySQL 的账号密码，或者 MySQL 服务没启动。先确认 `mysql -u root -p` 能登录，再改配置。

### Q4：启动报 `Port 8080 was already in use`？

关掉占用 8080 的进程（`netstat -ano | findstr :8080` 找到 PID 后结束），或临时改端口（不要提交改动）。

### Q5：提交时提示「检测到敏感文件 application-local.yml」？

这是**预期行为**：本机配置不允许入仓，钩子会拦截。确认你只提交代码；如果之前已经 `git add` 了它，执行 `git rm --cached src/main/resources/application-local.yml`。

### Q6：钩子完全没触发？

```bash
git config --get core.hooksPath    # 应为 .githooks
git config core.hooksPath .githooks
```

Windows 下必须通过 Git Bash 运行 `sh` 钩子；如果提交时没任何钩子输出，重新执行安装脚本，并确认 `.githooks/` 下有 `pre-commit`、`commit-msg`、`pre-push`。

### Q7：PR 显示 CI 失败 / 有冲突？

- CI 失败：点进 Actions 查看 `build` 日志，本地用同一条命令复现，修好再 push；
- 有冲突：在本地功能分支上 `git fetch origin && git rebase origin/main`，解决冲突后 `git push --force-with-lease`（只对**自己的功能分支**）。

### Q8：我不小心把代码提交到了本地 main？

```bash
git branch feature/my-change     # 把提交挪到新分支
git switch main
git reset --hard origin/main
git switch feature/my-change
```

如果已经 push 到远端 `main`：立刻通知 Owner，由 Owner 处理回滚。

### Q9：想用 AI 帮我写代码，有什么边界？

- AI 可以帮你查代码、写实现、跑命令、修 CI，但**提交信息、PR 描述、最终代码要你自己确认**；
- 不要在提示词里粘贴真实密码 / Key；本机配置让 AI 留空，由你手填；
- 答辩会问实现细节，交付前确保你能讲清自己的代码。
